# 模型产物审阅清单

用于审阅 `comms-optimize` 在真实项目中的改动。通过测试不等于可以保留改动；保留前至少检查以下项目。

## 1. 改动边界

- 是否只改了本轮目标文件和目标范围。
- 是否引入无关重构、格式化或大面积移动。
- 是否改了控制流、算法、公共 API 或依赖；若改了，是否有对应测试覆盖。
- 对 `real_projects/ModulationPy`，默认只接受低风险 docstring、注释、错误消息和测试补充；数值算法优化需单独立项。

## 2. 行为等价

- `scripts/check-real-project.ps1` 是否通过。
- 若修改调制、噪声、LLR、BER、星座映射或软/硬判决逻辑，是否补充了数值回归测试。
- 是否只依赖现有 2 个 unittest；如果是，是否明确说明覆盖不足。
- 是否存在只改错误消息但上层可能匹配异常字符串的风险。

## 3. 单位与术语

- 单位是否来自代码、论文、库文档或明确上下文，而不是模型猜测。
- 归一化星座、线性噪声方差、无量纲仿真量是否写成"归一化"、"线性值"、"无量纲"或"非 dB"。
- 不确定时是否避免写 `[V]`、`[W]`、`[Hz]` 等真实物理单位。
- 第三方项目原有英文术语、公开参数名、返回语义是否保持一致。

## 4. 可审阅性

- `git -C real_projects\ModulationPy diff` 是否能正常显示改动。
- diff 是否小到可以人工逐行审阅。
- 是否存在拼写修复、变量改名等看似低风险但可能漏改的内容；需用 `rg` 查残留。
- 如果决定不保留，是否已执行 `git -C real_projects\ModulationPy checkout -- .` 并确认工作区干净。

## 5. 结论

保留改动前应能回答：

- 改了什么。
- 为什么需要改。
- 如何验证行为等价。
- 还有什么风险。
- 是否需要提交到真实项目子仓库，还是仅作为闭环测试产物回退。
